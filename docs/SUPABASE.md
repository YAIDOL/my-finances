# Налаштування Supabase

Проєкт my-finances уже створено в YAIDOL's Org; міграцію finance_initial_schema застосовано. Реєстрація, вхід, приватність даних і конкурентні збереження перевірені через реальний API. Результати: [verification.md](verification.md). Нижче описано налаштування для повторного розгортання.

## Проєкт і міграція

1. Створіть окремий Supabase-проєкт для цього сайту або виберіть уже погоджений проєкт. Міграція призначена для нового проєкту без таблиць із такими самими назвами.
2. У **SQL Editor** виконайте весь файл `supabase/migrations/202610050001_finance.sql` як одну міграцію. Для керованої CLI-історії можна застосувати той самий файл через `supabase db push` після прив’язки правильного проєкту. Не запускайте міграцію повторно вручну: історію змін потрібно зберігати.
3. Перевірте, що таблиці `profiles`, `finance_state`, `user_preferences` мають увімкнений RLS, а функція `save_finance_state` існує. Supabase рекомендує захищати власні профілі через RLS і створювати їх тригером на `auth.users`. Несправний тригер може блокувати реєстрацію. [Документація профілів і тригерів](https://supabase.com/docs/guides/auth/managing-user-data).

## Обов’язкові налаштування Authentication

- Дозвольте реєстрацію нових користувачів (**Allow new users to sign up**).
- У **Authentication → Sign In / Providers → Email** увімкніть Email/password і **вимкніть Confirm email**. Нікнейм `alice_17` стає адресою `alice_17@users.my-finances.invalid`; це технічна адреса, яка не приймає листів. Без вимкнення підтвердження нові користувачі не зможуть увійти. [Парольна автентифікація](https://supabase.com/docs/guides/auth/passwords).
- Задайте **Minimum password length = 6**. Обов’язкові вимоги до наборів символів вимкніть, щоб допустимий пароль із шести символів відповідав погодженій поведінці. Індикатор надійності лише радить покращення.
- Не вмикайте OAuth, телефонну або анонімну реєстрацію для цього застосунку: тригер приймає лише нікнейм і відповідну технічну адресу.
- У **URL Configuration** задайте фактичну GitHub Pages адресу сайту як **Site URL**; до redirect allow list додайте цю адресу й `http://127.0.0.1:5173` для локальної розробки. Hash-маршрути працюють у статичному сайті без серверних rewrite-правил. Поточний вхід паролем не потребує email redirect.

**Відновлення пароля через email недоступне.** Не пропонуйте користувачу посилання «Забули пароль?» і не викликайте `resetPasswordForEmail` для цих адрес. Збережіть пароль у менеджері паролів. Адміністративне відновлення потребуватиме окремого погодженого процесу перевірки власника; його тут не реалізовано. Паролі передаються лише Supabase Auth, ніколи не входять до фінансового стану чи демоданих.

## Публічна конфігурація фронтенду

У локальному `.env.local` (цей файл не комітити):

```dotenv
VITE_SUPABASE_URL=https://PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Для старих проєктів замість publishable key можна використати `VITE_SUPABASE_ANON_KEY` з legacy **anon** key. Якщо обидва задано, пріоритет має publishable key. У GitHub Actions задайте ті самі значення як repository variables або secrets, доступні кроку Vite build. Після зміни перебудуйте та опублікуйте сайт: Vite підставляє конфігурацію під час збірки.

Проєктна URL і publishable/anon key є публічною конфігурацією. **Не використовуйте `service_role`, `sb_secret_...`, database password чи access token** у `VITE_*`, браузері або репозиторії. Доступ кожного користувача обмежують RLS та його Auth-сеанс. [Захист Data API](https://supabase.com/docs/guides/database/secure-data).

## Дані та конкурентні зміни

`profiles.username` є унікальним нормалізованим нікнеймом: 3–24 ASCII літери, цифри або `_`, нижній регістр. Тригер відхиляє неправильний нікнейм, відсутні metadata та адресу, яка не відповідає нікнейму. Клієнт задає `user_metadata.username` для відображення; це не джерело прав доступу. Профіль через API читає лише власник; користувач не може змінити свій username через таблицю.

`finance_state` містить одну приватну JSON-структуру з масивами `accounts`, `transactions`, `goals`, `debts`, `payments`, `budgets`, `categories`. Порожній новий профіль повертає версію `0`. Функція `save_finance_state(p_state, p_expected_version, p_expected_user_id)` перевіряє, що захоплений до початку асинхронної дії ID дорівнює `auth.uid()`, і бере власника рядка тільки з `auth.uid()`, блокує його рядок, перевіряє версію й записує весь стан із версією `+1` в одній транзакції. Початкові одночасні збереження з версією `0` дають одного переможця та один конфлікт. Прямі insert/update/delete фінансових рядків клієнтам не дозволено. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [права функцій](https://supabase.com/docs/guides/database/functions).

Конфлікт повертає `FINANCE_VERSION_CONFLICT`; клієнт показує українську інструкцію оновити сторінку. Програма має приймати новий стан лише після підтвердження нової версії сервером. Помилка читання, запису або мережі не означає порожній рахунок і не перемикає користувача на деморежим.

Таблиця `user_preferences` із власними RLS-політиками відокремлена від фінансової версії. Інтерфейс може зберігати налаштування пристрою локально; ця таблиця підготовлена для окремого збереження налаштувань у хмарі. Поточні обов’язкові `loadFinanceState` / `saveFinanceState` її не змінюють.

## Перевірка після підключення

До використання реальних фінансів виконайте перевірки в тестовому проєкті:

1. Зареєструйте `Alice_17` з допустимим паролем. Очікуйте активний сеанс, приватний профіль `alice_17`, порожні фінанси та версію `0`. Вийдіть і увійдіть як `ALICE_17` із тим самим паролем.
2. Спробуйте повторну реєстрацію того самого нікнейму, нікнейм із кирилицею, а через прямий Auth API — невідповідну технічну адресу чи відсутній `username`. Жодна спроба не має створити другий профіль або придатний новий обліковий запис.
3. Створіть користувачів A і B. Збережіть окремі стани. Сеанс B не має бачити профіль, налаштування чи фінансовий рядок A навіть із явно заданим ID A. ID у параметрі RPC є лише перевіркою очікуваного власника: ID A із JWT B повертає FINANCE_OWNER_MISMATCH без будь-якого запису. Старий двопараметровий RPC недоступний клієнтам.
4. Без авторизації SELECT до приватних таблиць і виклик save RPC не мають відкривати дані чи записувати стан. Авторизований прямий UPDATE/INSERT/DELETE до `finance_state` має бути відхилений.
5. Одночасно викличте два збереження з очікуваною версією `0` для нового користувача; лише одне має повернути `1`. Повторіть із двома збереженнями на однаковій наступній версії. Конфлікт не має частково змінювати дані.
6. Вимкніть мережу під час читання й запису. Очікуйте видиму помилку; уже підтверджений стан не має зникати або замінюватися демоданими.
7. Перезавантажте GitHub Pages сайт після успішного збереження, перевірте сеанс і збережені дані. Окремо перевірте новий браузер/пристрій. Помилка авторизації не має показувати фінанси попереднього користувача.

Підсумок проведених перевірок наведено у [verification.md](verification.md). Чекліст вище можна повторно використати після змін автентифікації чи міграцій.

## Оновлення категорій і перевірка власника

У підключеному проєкті застосовано `20261005214821_private_categories.sql` та `20261005215621_bind_finance_save_to_expected_owner.sql`. Для нової інсталяції застосуйте їх після початкової схеми. Міграції не змінюють фінансові суми чи RLS. Категорії входять до особистого JSON-документа; окремої загальнодоступної таблиці немає. Старі документи без categories читаються й мігрують на клієнті; після оновлення старий клієнт не має права стерти categories.

Очікуваний власник передається окремим параметром RPC й перевіряється сервером проти JWT. Двопараметрова функція лишається внутрішнім помічником без EXECUTE для PUBLIC, anon чи authenticated. Новий RPC має порожній search_path і доступний тільки authenticated.
